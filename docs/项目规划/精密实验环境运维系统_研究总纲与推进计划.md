# 无人值守精密实验环境智能管控与设备运维系统：研究总纲与推进计划

> 当前主项目研究框架  
> 首选场景：光学暗室等对光照、温湿度、空气质量、门禁和设备状态有要求的精密实验空间  
> 当前阶段：先建立分析框架，不继续扩写代码

## 1. 产品定位

系统面向需要长时间无人值守的精密实验空间，解决以下问题：

- 多点温湿度、VOC/CO₂、光照、门磁和设备状态分散，人工巡检效率低；
- 暗室异常开灯、温度越界、排风故障或设备掉线需要本地快速处理；
- 现场包含不同厂商的 RS485/Modbus、CAN、UART 或开关量设备；
- 网络中断时不能失去本地采集、告警和基本联动；
- 设备分散且维护周期长，需要远程配置、日志诊断和可靠升级；
- 研发和生产阶段需要快速自检、接口测试和故障定位。

系统不以“采集几个传感器”为核心卖点，而以**多协议接入、边缘自治、可诊断、可恢复升级和工程化分析**为核心。

## 2. 与 BMS 项目的边界

| 比较项 | 精密实验环境运维系统 | BMS 项目 |
|---|---|---|
| 首要目标 | 环境稳定、设备可用、远程运维 | 电池安全、保护、SOC/SOH 和能量管理 |
| 风险等级 | 业务连续性和设备保护为主 | 高压、电流、热失控等安全风险更高 |
| 核心数据 | 环境量、门禁、设备状态、能耗 | 单体电压、电流、温度、SOC/SOH |
| 核心接口 | RS485/Modbus、CAN、Ethernet/Wi-Fi | AFE I²C、CAN、FET/接触器控制 |
| 升级目标 | 多节点远程运维、减少停机、滚动升级 | 满足充放电/接触器安全门控，优先可控维护 |
| 无线策略 | 柜级/房间级网关可长期联网 | 通常复用上级网关，不给每个 BMS 增加无线 |
| 实验重点 | RTOS、网关、协议、日志、OTA、诊断 | AFE、保护、SOC、CAN IAP、低功耗 |

两项目复用通用升级状态机和调试方法，但分别维护需求、门控策略、测试矩阵和简历描述。BMS 的 OTA 文档不再为了覆盖运维系统而无限扩张。

## 3. 逻辑角色与现有板卡映射

产品方案先定义角色，再决定具体型号：

```text
现场采集终端
  → 边缘控制网关
    → 网络通信模块
      → 本地维护工具 / 远程平台
```

| 逻辑角色 | 产品职责 | 当前原型载体 | 产品选型是否冻结 |
|---|---|---|---|
| 现场采集终端 | 传感器、输入输出、滤波、局部告警、有线通信 | STM32F103C8T6 小板 | 否 |
| 边缘控制网关 | 多总线接入、状态机、日志、看门狗、离线自治 | STM32F407ZGT6 学习板 | 否 |
| 网络通信模块 | Wi-Fi/BLE/MQTT、远程配置、升级包下载 | ESP32-S3 N16R8 | 否 |
| 维护工具 | 报文观察、节点模拟、本地升级、故障注入 | PC、MQTTX、USB-CAN | 工具链 |

原型板证明方法可行，产品型号由第一阶段的选型矩阵决定。最终可能保留这些型号，也可能选择更小封装、更合适容量或成本更低的同类器件。

## 4. 总体软件架构研究框架

```text
应用装配层
  └─ 启动顺序、依赖注入、模式选择、配置加载
业务与状态机层
  ├─ 领域模型：设备、点位、样本、告警、策略、命令、事件
  ├─ 状态机：环境、告警、联动、运维、升级
  └─ 纯决策逻辑：输入事实，输出 Command / Event
服务层
  ├─ 采集、配置、日志、诊断、升级等用例编排
  └─ 依赖领域模型以及传输、存储、时钟和设备抽象
传输/协议适配层
  ├─ ITransport / IMessageBus 等端口
  └─ Modbus RTU、自定义帧、CAN、MQTT 等适配器
设备驱动层
  ├─ 传感器、EEPROM/Flash、UART、CAN、RS485、看门狗
BSP/HAL
  └─ 时钟、GPIO、DMA、中断、定时器和芯片平台适配
```

这里采用的是“轻量领域模型”，不是把服务器端 DDD 框架照搬进 MCU。领域层只由 C 结构体、枚举、状态机和尽量无副作用的决策函数组成，不直接依赖 FreeRTOS、HAL、MQTT 或某颗传感器。这样，Modbus 寄存器、CAN 信号和 MQTT JSON 都先转换为相同的 `Point/Sample/Event`，业务规则无需为每一种协议重写。

依赖方向原则如下：

```text
BSP/HAL → 驱动 → 协议适配 → 服务编排 → 领域决策
                 外部实现 ──→ 抽象端口 ←── 内部用例
```

箭头表示“外层知道内层”，领域层不知道外设和操作系统。中断只产生最小事件，服务层负责排队和编排，领域层负责判断，驱动层负责执行最终硬件命令。

架构研究需要回答：

- 各层能否单独替换和测试？
- 哪个模块拥有数据，谁只能读取快照？
- ISR、任务、协议回调和业务状态机之间怎样传递事件？
- 哪些接口同步，哪些异步，超时和取消怎样表达？
- 网络故障、传感器故障和存储故障如何降级？
- 哪些模块可以复用当前 ESP32 工程的经验？

## 5. 软件流程研究框架

后续每条流程都输出一张时序图或状态机，再配少量伪代码。

### 5.1 启动流程

```text
复位原因和安全输出初始化
→ 时钟/内存/中断
→ NVM 和配置恢复
→ 通信外设和设备探测
→ 创建 RTOS 对象与任务
→ 启动采集和本地控制
→ 启动网关/网络通信
→ 自检结果和设备状态上报
```

研究点：为什么安全输出先初始化、某个设备失败是否阻止系统启动、任务创建前后哪些资源有效。

### 5.2 采集与处理流程

```text
定时触发/传感器中断
→ 驱动读取
→ CRC/范围/时间戳检查
→ 滤波和质量标记
→ 更新权威快照
→ 通知告警、日志和上报任务
```

研究点：周期精度、DMA/中断/轮询取舍、坏数据是否覆盖旧有效值、队列满怎样处理。

### 5.3 告警与联动流程

```text
新测量/设备事件
→ 阈值 + 迟滞 + 持续时间
→ 状态机转换
→ 本地输出
→ 记录事件
→ 异步上报
```

研究点：为什么不能一次超限就动作、传感器失效时如何进入降级状态、远程命令能否覆盖本地规则。

### 5.4 通信流程

研究 RS485 主站轮询、CAN 心跳/事件、UART DMA 帧解析和 MQTT 会话恢复四类流程，重点解释缓冲区、消息队列、超时、重试、幂等和总线负载。

### 5.5 配置和日志流程

配置采用候选值校验、应用、持久化、提交或回滚；日志采用分级、异步写入、环形覆盖和写入限频。

### 5.6 运维系统升级流程

运维系统侧重点是：

- 网关和多个终端的版本清单；
- 兼容矩阵和分批/滚动升级；
- 网络中断后的断点恢复；
- 不影响未升级节点继续运行；
- 升级状态、进度、错误阶段和审计；
- 网关自身升级与下级节点升级分开编排。

与 BMS 相比，它不需要反复展开电流、接触器和均衡等专用门控；BMS 文档只保留这些安全差异以及 CAN IAP 资源约束。

## 6. 硬件选型研究框架

### 6.1 先完成需求和预算

每个逻辑角色建立以下表格：

1. GPIO/复用引脚预算；
2. UART、SPI、I²C、CAN、USB、Ethernet 数量；
3. 定时器、PWM、ADC、DMA 和外部中断需求；
4. Flash：Bootloader、App、升级槽、常量和文件系统；
5. SRAM：全局数据、任务栈、队列、DMA 缓冲区、网络缓冲区和堆；
6. 主频和最坏 CPU 负载；
7. 工作温度、供电、低功耗和启动时间；
8. 单价、供货、封装、PCB 层数和调试成本。

### 6.2 候选方向，不立即定型

- 现场终端：比较 F103C8/CB、STM32G0/G4 或兼容国产 MCU，重点是 CAN、DMA、Flash/SRAM 和成本；
- 边缘网关：比较 F407 不同封装/容量、同级国产 MCU 或带更合适网络外设的型号，避免直接把 144 引脚学习板型号当量产答案；
- 无线模块：比较 ESP32-C3、ESP32-S3 不同 Flash 容量以及模块认证成本；只有需要 USB、更多 GPIO、PSRAM 或更大应用时才选择更高规格；
- 存储：比较内部 Flash、EEPROM、FRAM 和 SPI NOR 在寿命、容量、原子更新与升级暂存方面的差异；
- 现场总线：根据距离、节点数、实时性、隔离和现有设备生态决定 CAN 与 RS485 是否同时保留。

最终输出不是“哪个芯片参数最大”，而是一份可追溯的选型决策记录。

## 7. 面试知识点框架

两份 100 题资料先按下列矩阵归档，当前不展开答案。

### 7.1 芯片类

- Cortex-M3/M4、FPU、NVIC、中断优先级和临界区；
- 时钟源、PLL、总线分频、外设时钟和时钟故障；
- Flash/SRAM、堆栈、链接脚本、Bootloader 和向量表；
- DMA、ADC、定时器、PWM、RTC、低功耗和看门狗；
- 复位原因、HardFault、调试口和量产启动模式。

### 7.2 系统类

- FreeRTOS 任务划分、优先级、阻塞、抢占和时间片；
- 队列、任务通知、事件组、二值信号量、互斥锁和优先级继承；
- 软件/硬件定时器、周期漂移和 `vTaskDelayUntil`；
- 栈水位、堆碎片、CPU 占用、看门狗和任务存活；
- 状态机、数据所有权、错误码、日志和故障降级。

### 7.3 接口类

- I²C：起始/停止、地址、ACK/NACK、上拉、速率、总线恢复；
- SPI：主从、三/四线、全/半双工、CPOL/CPHA、片选和速率来源；
- UART/RS485：波特率、帧格式、DMA、空闲中断、收发切换和终端电阻；
- CAN：仲裁、位时序、过滤器、错误状态、总线负载、心跳和应用协议；
- Ethernet/lwIP/TCP：PHY、MAC、缓冲池、连接状态、重传和断线恢复；
- Wi-Fi/BLE/MQTT：连接、QoS、Keep Alive、Retain、会话和安全。

### 7.4 功能类

- 多传感器采集、滤波、标定和数据质量；
- 告警迟滞、持续时间、联动和本地自治；
- 参数持久化、冗余、磨损和断电一致性；
- 日志、HardFault、复位原因和远程诊断；
- OTA/IAP、Manifest、校验/签名、防降级、回滚/可恢复；
- 工厂自检、接口回环、长稳和故障注入。

每一阶段只选择与当前方案直接相关的问题，形成“原理-特性-应用-调试”的口述答案。

## 8. 选择性实操与调试计划

不追求所有功能上板，优先选择能覆盖核心能力的实验：

| 优先级 | 实验 | 证明什么 |
|---|---|---|
| 已完成 | ESP32 采集、BLE/Wi-Fi/MQTT、NVS、A/B OTA | 服务分层、并发、网络、持久化和可靠升级 |
| P0 | F407 + USB-CAN 收发、过滤和错误状态 | CAN 原理、位时序、ISR/任务解耦和总线调试 |
| P0 | F407 时钟与双时基检查 | 时钟树、定时准确性和故障定位 |
| P1 | F407 UART DMA + 环形缓冲区 | DMA、空闲中断、流式协议和队列 |
| P1 | ESP32 与 F407 最小帧协议联调 | 跨 MCU 分层、超时、序号、CRC 和恢复 |
| P1 | RTOS 任务优先级/队列/互斥实验 | 调度、阻塞、竞态和资源保护 |
| P2 | F103 CAN 节点或最小 CAN IAP | 资源受限设计、Bootloader 和可恢复升级 |
| P2 | RS485/Modbus 单设备轮询 | 半双工、CRC、超时和总线物理层 |

每项实验先单功能，再联合调试；遇到问题时同步整理“现象-分层排查-根因-修复-复测”的面试答案。

## 9. 数日推进计划

### 第 1 阶段：产品需求与硬件选型

- 冻结暗室/精密实验环境的用户、功能边界和非目标；
- 建立角色级接口、引脚、Flash/SRAM、性能和成本预算；
- 输出候选 MCU/模块对比和选择理由。

### 第 2 阶段：软件架构

- 完成分层组件图、任务表、优先级和 IPC 选择；
- 明确中断、任务、协议回调和数据所有权；
- 输出资源预算和风险点。

当前状态：核心设计基线已完成，详见 [阶段二：软件架构、任务与 IPC 设计](阶段2_软件架构与任务IPC设计.md)。后续实操需要回填 DMA 冲突、栈高水位、队列水位和主机协议台架证据。

### 第 3 阶段：软件流程

- 完成启动、采集、告警、通信、配置、日志和升级流程；
- 使用时序图、状态机和伪代码，不抄写整套实现；
- 给每条流程补失败路径。

### 第 4 阶段：面试题与官方资料

- 按芯片、系统、接口、功能四类选择高频问题；
- 以官方手册复核答案；
- 形成可以口述的“原理-特性-应用-调试”提纲。

### 第 5 阶段：选择性实操

- 完成一条 CAN 台架、一条 DMA/串口链路和一个 RTOS 并发问题；
- 复用已经完成的 ESP32 采集、MQTT 和 OTA 证据；
- 记录关键日志、波形、故障注入和解决过程。

### 第 6 阶段：简历与模拟面试

- 将项目压缩为背景、职责、难点、方案、指标和结果；
- 为每个简历 bullet 标记内部证据等级；
- 使用两份题库做针对性追问，不追求机械背完全部题目。
