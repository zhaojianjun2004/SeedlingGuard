# 项目上下文与决策记录

> 本文件只保存跨阶段必须保留的事实、边界和已确认决策。详细原理见各阶段学习与设计文档。

## 1. 当前 ESP32 实验项目

- 硬件：ESP32-S3 N16R8 开发板，默认使用板载 PCB 天线。
- 供电：开发板可通过 USB Type-C 供电。
- 传感器：AHT20，通过 I²C 采集温湿度。
- 第一阶段已经完成并验证：AHT20、FreeRTOS 采样服务、BLE、Wi-Fi、MQTT、NVS 配置持久化。
- 当前实验项目是后续架构和调试方法的可运行载体，不等同于运维系统或 BMS 的最终产品硬件。
- 第二阶段已经实现 ESP32 A/B OTA、首次启动自检、确认/回滚，以及 BOOT 键长按触发的 HTTP 下载链路。`1.1.1 -> 1.1.2` 的下载、槽位切换、pending verify 和确认有效已经完成开发板实机验证。

## 2. BMS 目标产品背景

- 核心 MCU：STM32F103C8T6。
- 主要器件：BQ76940、BQ76200、BQ34Z100-G1。
- BQ76940 是当前实际做过调试的主要器件。
- BQ76200 和 BQ34Z100-G1 目前以系统设计和理论分析为主，不能描述成已经完成实机验证。
- BMS 产品计划使用 CAN 完成数据上报、诊断，并评估自定义 CAN IAP。
- 普通 STM32F103 的片内 ROM Bootloader 只提供 USART1 下载；CAN IAP 需要位于用户 Flash 的自定义 Bootloader。

## 3. BMS 硬件当前状态

- 电池包输入相关引脚已经损坏，无法继续可靠获取真实电芯电压。
- USB 转 TTL 已损坏。
- 原板充电/供电及 3.3 V 转换部分疑似损坏。
- 不应直接使用 F407 学习板的 3.3 V 给故障板强行供电，必须先排查短路、反向灌电和稳压器负载风险。
- 已有 USB-CAN 调试器。
- 后续可使用 STM32F407 学习板加合适的 CAN 收发器，与 USB-CAN 建立独立、干净的 CAN 台架，不依赖损坏的 BMS 板。
- `ziliao` 目录包含 BMS 参考资料，当前阶段不进行全面展开，需要时按具体问题查阅。

## 4. 已确认的架构决策

1. BMS 产品目标仍以 F103C8T6 为资源约束对象，不为追求表面差异随意改成 F407。
2. F407 定位为学习板、CAN 测试节点和调试工具，不冒充最终 BMS 核心板。
3. ESP32 定位为 OTA/回滚、网络通信、状态机和故障注入实验平台。
4. BMS 产品优先复用现有 CAN；无线能力放在网关、T-Box 或维修工具，不默认给每个 BMS 增加 Wi-Fi/BLE。
5. SWD 和 USART1/BOOT0 应作为 F103 的产线及最终救援通道。
6. 必须区分“单槽升级失败后还能重新刷写”和“保留旧镜像并自动回滚”。前者是可恢复，后者才是真正回滚。
7. 项目说明必须区分实机验证、模拟验证和理论设计，避免夸大完成度。

## 6.1 当前产品化方向与研究方法

- 简历主项目暂定为“无人值守精密实验环境智能管控与设备运维系统”，优先以光学暗室为具体场景；它与 BMS 项目分开研究。
- 产品硬件型号不被手头开发板锁定。F103C8T6、F407ZGT6 和 ESP32-S3 N16R8 是原型载体，最终型号通过成本、引脚、接口、Flash/SRAM、性能、低功耗和可靠性分析决定。
- 项目研究以硬件选型、软件架构、软件流程、知识点/面试题四条主线推进；代码只验证关键假设，不追求实现所有设想功能。
- 理论研究可以进入简历，但内部证据持续区分实机验证、台架/模拟验证和设计研究；描述分别使用“实现/验证”“模拟/联调”“设计/评估”等准确动词。
- 调试采用单功能、模块联调、系统联调和故障注入的顺序，挑选 CAN、DMA/串口、RTOS 并发、升级等核心链路实操。
- 两份 100 题 PDF 用作问题索引，答案必须结合项目并优先由官方手册复核，不能直接照背。
- BMS 项目暂时冻结，等待用户明确指令；已有升级文档保留，但不与运维系统重复扩写。
- 软件架构采用轻量领域模型：`Device/Point/Sample/Quality/Rule/Alarm/Command/Event` 只表达业务语义和状态，不依赖 FreeRTOS、HAL 或具体协议；服务层负责编排，协议层负责转换，驱动层负责硬件执行。
- 产品第一版采用“两级控制 + 可选分布节点”：边缘 MCU 负责本地权威状态和策略，ESP32 类模块负责无线通信与远程下载；传感点集中时不强制增加现场 MCU。
- 当前选型判断：F103C8 保留为资源受限教学/台架节点，F407ZG 为网关原型载体，ESP32-S3 为网络与 OTA 实验载体；量产候选继续比较更大容量 F103/STM32G0B1、F407VG 级网关和 ESP32-C3 模块，尚未冻结具体料号。
- 阶段一点位基线：24 个输入点、4 个控制点；架构支持 4～16 个现场节点，第一轮台架只验证 1～2 个。消防信号只接收合规控制器干接点，本系统不替代消防控制器。
- F407VG/LQFP100 已完成纸面引脚复用预评审，可同时安排 RMII、双 CAN、RS485、ESP32 UART、SPI NOR、I²C、USART 调试与 SWD；这不等于当前 F407ZG 学习板可以照表接线，实操仍需结合学习板原理图和 CubeMX 检查 DMA/时钟冲突。
- F407 网关升级保留两种布局：应用长期小于约 320 KiB 时评估片内双槽；应用更大时使用 SPI NOR 保存新旧镜像，由可靠 Bootloader 恢复安装。F407 的 64 KiB CCM 不可存放 DMA 缓冲。

## 7. 第二阶段当前实现边界

- 固件版本：开发板当前运行并已确认的版本为 `1.2.1`（`ota_1`）；当前源码、`build/0_helloworld.bin` 和 `build/manifest.json` 同为 `1.2.1 / release_sequence=121`，故障注入已关闭。
- 分区：`ota_0` 和 `ota_1` 各 2 MiB，包含 `otadata`，Bootloader 回滚已启用。
- 触发：`1.1.2` 仍从编译期裸固件 URI 下载；`1.2.0` 起长按 BOOT 会请求编译期 Manifest URI。串口交互控制台保留但默认关闭。
- 已检查：Manifest 长度/Schema/字段唯一性和类型、产品、硬件、版本、发布序号、Content-Length、ESP 镜像头、Manifest 与镜像一致性、流式 SHA-256 和 ESP-IDF 镜像完整性。
- 尚未实现：HTTPS 身份校验、数字签名与可信公钥、运维系统升级策略和 MQTT 升级管理面；当前按研究计划暂缓代码扩展。
- 编译结果：ESP-IDF v5.1.2 全量构建通过；当前 `1.2.1` 固件为 `0x113bd0` 字节，每个 2 MiB 槽剩余约 46%，Manifest 大小和 SHA-256 已与二进制核对一致。
- 已验证结果：`1.1.1` 从 `ota_0` 运行，下载 1124496 字节的 `1.1.2` 到 `ota_1`，首次启动为 `pending_verify`，5 秒后自检通过并标记为 `valid`。
- 已验证结果：故障版 `1.1.3` 从 `ota_1` 下载到 `ota_0` 并启动，自检主动失败后 Bootloader 自动回到已确认的 `1.1.2/ota_1`。
- 已验证结果：`1.1.2` 通过旧裸固件入口成功安装并启动 `1.2.0` Manifest 能力引导版本。
- 已知实验硬件问题：AHT20 小模块引脚未焊接，采集失败属于接触不良；它是外部可恢复依赖，按设计不参与 OTA 镜像有效性判定。
- 已验证结果：`1.2.0` 通过 Manifest 请求并完成 `1.2.1 / release_sequence=121` 升级，镜像大小和流式 SHA-256 校验通过；首次启动自检后标记为 `valid`，手动复位后仍从 `ota_1` 正常运行。
- 下一步代码阶段：暂缓。先按精密实验环境运维系统研究总纲，从产品需求与硬件选型开始分析。
