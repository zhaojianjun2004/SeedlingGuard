# 工业现场环境监测物联网边缘网关：代码实施路线

> 2026-10-07 走读 `0_helloworld` 后形成。此文档确定实现顺序与验收边界，尚不是完成报告。  
> 本轮决定：局域网页面采用 HTTP JSON 定时轮询，不使用 WebSocket。

> 2026-10-08 硬件路线已确定：F407↔ESP32-S3 先用 UART；F407 板载 CAN2↔USB-CAN/电脑单独验证。ESP32-S3 虽有 TWAI 控制器，但当前没有 CAN 收发器，不能直接接 CANH/CANL。F407 工程实际生成在 `fireware/stm32f407/`，与原规划的 `firmware/` 拼写不同，暂不移动。

## 1. 先给结论

在现有 `0_helloworld` 上演进 ESP32-S3 网关软件，现场控制器工程现位于同一仓库的 `fireware/stm32f407/`。参考两份开源方案的功能和模块边界，但不整仓移植 F411 代码：它的芯片型号、外设映射和部分故障处理与目标工程不一致。先建立能端到端运行的最小闭环，再补 AP 配网、离线缓存和诊断；已有 ESP32 OTA 保持可用。

第一条闭环是：**两路 Modbus 仪表 → F407 数据质量 → UART 帧 → ESP32 状态快照 → MQTT 与 HTTP 页面；网页/云命令 → UART 帧 → F407 执行结果 → 页面/云状态**。F407 的 CAN2 另外与 USB-CAN/电脑完成收发、过滤器和 Bus-Off 实验。AHT20 现有直连代码保留作单板实验入口，不作为这条现场链路的数据来源。

代码走读中需先修正的一点：旧 MQTT 快照只携带 `valid`，却仍格式化温湿度数值；网关上报必须携带 `quality` 与采样时间/年龄，并对无效点位使用明确的空值或质量字段，不能把最后读数冒充实时读数。

## 3. 固定的第一版范围

### 3.1 包含

1. 两个 Modbus RTU 从机：温湿度仪表与光照仪表，地址/寄存器映射在配置表中定义；支持功能码 03、CRC16、超时、异常响应和单设备降级。
2. F407 `USART3 PD8/PD9` ↔ ESP32-S3 `UART1 GPIO18/GPIO17` 作为板间候选接线，115200、8N1、3.3 V TTL、共地；消息带版本、长度、序号和 CRC。另以 F407 CAN2 ↔ USB-CAN/电脑验证经典 CAN 标准帧、125 kbps。
3. F407 持有采集启停和采样周期；ESP32 网页、MQTT 只发起命令，收到 F407 执行结果后更新状态。本地按键待 CubeMX 引脚确认后再加入。
4. ESP32 STA 连接、AP 配网、NVS 凭据；局域网页面用 HTTP `GET` 轮询 JSON 状态，用 HTTP `POST` 提交命令。
5. MQTT 遥测 QoS 1、命令订阅、连接状态、离线持久队列及 Broker 确认后推进队列。
6. 现场设备、板间 UART、F407 CAN2、Wi-Fi、MQTT、缓存的诊断计数与恢复路径；保留 ESP32 A/B OTA。

### 3.2 暂不并入主线

项目不加入 LVGL 触摸屏。ESP32 侧 CAN/TWAI、F407 远程 IAP、复杂继电器联动、OneNet 专有物模型、HTTPS 网页、跨板“每条遥测绝不丢失”的承诺暂不纳入第一版。云端先对接标准 MQTT Broker，平台适配层不进入板间协议。

## 4. 核心协议与数据模型先冻结

### 4.1 板间 UART 帧 V1

```text
SOF[2]=A5 5A | version[1] | type[1] | seq[2] | len[1] | payload[0..32] | CRC16[2]
```

多字节整数用小端；CRC16 先采用 Modbus RTU 同款 `CRC-16/MODBUS`（初值 `0xFFFF`、反射多项式 `0xA001`），覆盖 `version` 到 `payload`，低字节先发。最大载荷 32 字节；接收端先校验长度再等完整帧，CRC 错误时按 SOF 重新同步。逻辑消息 `STATUS(0x01)`、`SAMPLE(0x02)`、`COMMAND(0x10)`、`RESULT(0x11)`；状态含启动会话号、实际采集开关和周期，样本含 `point_id、quality、scaled_value、sample_age_ms`。F407 保留真实最后成功时间；ESP32 用接收时间减年龄得到近似采样时刻。无可信 UTC 时上报设备运行时间和启动会话号。

控制命令只做幂等的“设置为某状态/周期”，不用“翻转状态”帧。ESP32 将 HTTP/MQTT `request_id` 映射到 UART 帧的 `seq`，超时后查询 F407 实际状态；同一序号的重试不产生相反结果。UART 帧完整接收、F407 执行回执、MQTT PUBACK 分别代表不同层次。

### 4.2 F407↔电脑 CAN 诊断帧

CAN2 先与现有 USB-CAN/电脑建立 125 kbps 两节点台架，使用 11 位标准 ID。第一轮 `0x100` 发送现场状态、`0x200` 发送单测点；接收和命令通道可在 UART 主链路稳定后再加。CAN 诊断的序号、点位与质量语义复用 `shared/protocol` 中的领域模型，不把 UART 帧头直接塞入 8 字节 CAN 载荷。CAN Bus-Off 只降级电脑诊断链路，不改变 F407 的 Modbus 采集和 UART 上报。

### 4.3 统一状态与 HTTP API

- `GET /api/status`：返回 `field_online`、启动会话号、实际采集开关和周期、各测点 `value/quality/sample_age_ms`、UART 错误、Wi-Fi/MQTT 状态、缓存深度；页面每 1～2 秒轮询。
- `POST /api/commands`：`{request_id, op, value}`，只入统一命令队列，返回 `202` 与命令 ID；不在 HTTP 回调中阻塞等待 UART 执行回执。
- `GET /api/commands/{request_id}`：返回 `PENDING/APPLIED/FAILED/TIMEOUT` 和实际状态。MQTT 下行命令也调用同一控制服务。
- `POST /api/wifi`：只在配网模式开放，验证 SSID/密码长度与格式；连上并取得 IP 后再持久化候选凭据。

本地按键暂不纳入首轮 CubeMX 生成与软件验收；ESP32 的 BOOT 键已经用于 OTA 长按触发，不复用成采集启停键。后续确认 F407 可用按键引脚后，再让它进入同一领域命令路径。

## 5. 代码目录与依赖边界

```text
0_helloworld/
├── components/
│   ├── gateway_protocol/      # ESP-IDF 对共享纯 C 协议库的组件封装
│   ├── field_state/           # ESP32 测点快照、心跳和质量失效
│   ├── uart_link/             # ESP32 UART1 与 F407 的帧链路
│   ├── gateway_control/       # 网页/MQTT 统一命令状态机
│   ├── gateway_web/           # esp_http_server + 静态单页 + HTTP JSON
│   ├── offline_store/         # 专用分区、记录 CRC、单写者、断电恢复
│   ├── wifi_manager/          # 扩展现有 STA 为 AP/STA 配网
│   ├── mqtt_service/          # 改为网关快照、命令适配和 QoS 1 确认
│   └── ...                    # 现有 AHT20/BLE/OTA 组件继续保留
├── fireware/stm32f407/
│   ├── stm32f407.ioc          # 芯片与外设配置来源，实际文件名以 CubeMX 输出为准
│   ├── app/                   # Modbus、点位质量、UART、CAN 诊断、控制与监督
│   ├── bsp/                   # HAL 与板级接口
│   └── tests/                 # 与硬件无关的协议/状态机测试
├── shared/protocol/           # F407/ESP32/主机测试共用的领域消息与 UART 帧编解码
└── docs/独立项目_物联网边缘网关/
```

在 F407 侧，Modbus 轮询任务独占 RS485 总线，领域任务串行应用控制命令，USART3 RX 与 CAN2 RX 中断只收帧并投队列，Flash 若加入则由单一存储任务访问。ESP32 侧 MQTT/HTTP 回调也只投命令，不直接修改 F407 状态镜像。避免从 F411 仓库复制无条件喂狗、发送即删缓存及注释掉互斥锁的实现。

## 6. 实施顺序与每阶段验收

| 阶段 | 代码工作 | 完成判据 |
| --- | --- | --- |
| 0. 基线保护 | 记录当前构建配置、分区和 OTA 健康检查；确认旧应用仍可编译 | 不覆盖既有未提交文档；旧 AHT20/MQTT/OTA 基线可复现 |
| 1. 协议和模拟链路 | 实现共享 UART 帧编解码、点位质量、命令状态机；建立主机端金样例和两端模拟收发 | 长度/CRC、字节序、序号回绕、重复帧、超时和重启会话测试通过 |
| 2. F407 现场侧 | CubeMX 建 F407ZGT6 工程；USART2/RS485 Modbus 主站、USART3 板间链路、板载 CAN2、FreeRTOS，后续加 IWDG 监督 | 固件可编译；Modbus 正常/CRC 错/超时/异常码路径可复现；CAN2↔USB-CAN 收发通过 |
| 3. ESP32 网关最小闭环 | UART1 接收和状态快照、HTTP 只读页面、MQTT 网关遥测；旧 AHT20/BLE 不再作为网关依赖 | 模拟 UART 帧可在 `/api/status` 与 MQTT 看到同一质量状态；F407 重启/断线后状态正确降级 |
| 4. 统一控制 | HTTP、MQTT 接入同一命令服务，UART `COMMAND/RESULT` 交互 | 范围校验、重复请求、超时、同时下发和执行后回读一致 |
| 5. 配网与持久化 | AP/STA 配网、NVS 凭据、HTTP 配网页面；增加离线分区与 QoS 1 补传记录状态机 | 无凭据可配网；失败可重试；断网/复网及补传中断电后队列能恢复；仅 Broker 确认后推进已完成状态 |
| 6. 可靠性与运维 | CAN2 Bus-Off、UART 断线、诊断计数、看门狗进展门控、ESP32 OTA 与新装配自检 | 故障注入和回滚路径可复现；无条件喂狗或错误确认不会掩盖失败 |

先做一个最小演示链：`F407 模拟两路 Modbus 数据 → UART → ESP32 → HTTP 状态/MQTT`，同时单独完成 `F407 CAN2 ↔ USB-CAN/电脑`。这样从阶段 3 起就有可观察的双板端到端结果；离线缓存、配网和升级属于随后加强的完整性工作。

## 7. 开始编码前的硬件核对

霸天虎 V2 的原理图已经确定板载 CAN2 `PB12/PB13`、USART2/RS485 `PA2/PA3` 和方向脚 `PC0`、SPI1 Flash `PB3/PB4/PB5/PG6`，HSE 为 25 MHz。板间 UART 暂选 USART3 `PD8/PD9` 到 ESP32-S3 UART1 `GPIO18/GPIO17`，连接前要核对两块开发板的引出脚、交叉 TX/RX 和共地；F407 的 CAN2 用现有 USB-CAN 验证。具体器件丝印、CAN 终端和传感器寄存器表也要核实。详见 [CubeMX 配置清单](CubeMX配置清单_霸天虎V2.md)。

现有电脑可找到 STM32CubeMX、Arm GNU Toolchain、CMake/Ninja 和本地 STM32F4 HAL 文件；ESP32 工程使用现有 ESP-IDF 版本。F407 工程以 `.ioc` + GCC 可复现构建为目标，避免只有 IDE 私有设置才能编译。
