## 3. 任务和数据所有权

F407 有 LinkTask、FieldTask、ModbusTask、StorageTask、SupervisorTask。StorageTask 在启动时加载配置和扫描日志，其他业务任务等待启动就绪后才工作。

- ModbusTask 独占 RS485 总线，采样结果投 `g_samples`，附取得时间和配置版本。
- FieldTask 是配置、测点和告警状态的唯一业务写者。每轮最多一条命令、四条采样，然后检查存储结果、数据年龄和事务期限。
- 配置更新先作为候选提交 StorageTask；FieldTask 仍继续处理采样，保存完成后才切换活动配置并回 RESULT。保存失败不会提前显示成功。
- LinkTask 复制快照后序列化。UART 发送只由该任务执行，CAN 中断只投递事件；CAN 故障不阻塞 RS485。
- StorageTask 独占 SPI Flash。配置完成使用独立长度 1 的结果队列，不与普通样本争用。
- SupervisorTask 检查各任务给出的当前阶段期限，只有全部正常时刷新 IWDG。

ESP32 的 UART 接收任务只收帧、更新快照与匹配回执。HTTP、MQTT 和串口都向 CommandTask 投递；该任务串行发送现场命令。MQTT 的 JSON 命令处理另有入口任务，现场等待不会卡住 PUBACK 和上报循环。gateway_storage 任务独占待发队列的运行期 NVS 操作。

## 4. 设备与采集参数

| 区域 | 温湿度地址 | 光照地址 | 测点 ID |
| --- | --- | --- | --- |
| 1 | 1 | 2 | 1 温度、2 湿度、3 光照 |
| 2 | 3 | 4 | 4 温度、5 湿度、6 光照 |
| 3 | 5 | 6 | 7 温度、8 湿度、9 光照 |

温度为有符号 0.1℃，湿度为 0.1%RH，光照为整数 lx。默认温湿度从 `0x0001` 读两个寄存器；光照从 `0x0002` 读两个寄存器，高低字拼接后除以 1000。**这些仍继承参考映射，必须按实际 RS-WS-N01-2D、RS-GZ-N01-2 手册确认顺序、地址和倍率**，入口为 `Config/modbus_profile.h`。

RS485 为 9600 8N1。现场默认每设备 5 s 到期轮询，允许周期 5000～600000 ms。单次发送结束后的响应收集期限 200 ms，健康设备首次失败最多再试一次，异常响应不当作无响应重试。请求前等待至少 5 ms 总线静默，噪声持续时也设置有界等待。

连续三轮通信失败降为 OFFLINE，此后每 10 s 单次探测，连续两次成功后恢复。异常响应另标为仪表异常；数据超量程可以导致测点 FAULT，但不应被解释为物理总线掉线。

设备状态为 0 未确认、1 在线、2 通信可疑、3 离线、4 仪表异常；测点质量为 0 INVALID、1 VALID、2 STALE、3 FAULT。全局采集停用用独立使能表达，不新增 Disabled 质量枚举。

## 5. 告警与时效

默认台架阈值：温度 10～35℃、湿度 30～90%RH、光照 100～50000 lx。温度恢复回差 1℃、湿度 3%RH、光照 100 lx。默认值不是所有作物通用的农艺指标。

连续三个有效样本越限后 ACTIVE；连续三个样本回到带回差的恢复范围后恢复。无效样本清空连续计数并进入 UNKNOWN，已经确认的告警保持锁存历史，不能因仪表失联就恢复。状态枚举为 0 NORMAL、1 PENDING、2 ACTIVE、3 UNKNOWN。

失败保留旧值与原取得时间；现场端独立检查 `2 × 周期 + 2 s` 的新鲜度。停采或配置切换后旧样本变 STALE。ESP32 再按携带的样本年龄和接收后经过时间判断，不把跨网关重启的旧样本时间强行夹成“刚采到”。

## 6. 持久化与事件追补

W25Q 仅接受已识别的 Winbond JEDEC 容量，拒绝未知器件。配置区 A/B 各 4 KiB，地址 `0x0000`、`0x1000`；事件区从 `0x2000` 开始，占 256 KiB，4096 个 64 字节槽。配置和日志均先写正文与校验，再写提交标记；日志尾部不完整记录在启动时被忽略。

事件类型：1 告警状态变化、2 测点故障/恢复、3 设备离线/恢复。事件 JSON 的 `state` 在类型 3 时表示设备状态，其余表示测点告警状态，`quality` 独立表示测点质量。记录保存事件号、原始启动标识、uptime、测点、质量和数值。循环覆盖意味着长期离线可能覆盖最旧日志；存储投递暂满时有 32 条 RAM 待补记缓冲并保持事件顺序；超过缓冲容量或写失败会计数，不能承诺无限或逐样本无损。

已提交的现场事件按最老未确认记录发送。ESP32 将事件写入 outbox 并提交事件追补位置后，通过 QUERY_EVENTS 告知现场当前位置。现场不能因为 UART 发送成功就推进；丢帧和网关重启后会重复发送，由持久位置去重。若主动清空 F407 日志或换板，应同步处理 ESP32 的事件追补位置，不能混用两个历史序列。

ESP32 `outbox` 为独立 **NVS** 分区，1 MiB，1024 条逻辑上限；沿用已有 NVS 实现，没有在此次重构中改为裸 Flash 文件系统。普通遥测最多使用 896 条，预留 128 条给事件；10 s 一条普通遥测约覆盖 149 分 20 秒。事件数、已有积压和写失败都会影响余量，容量不等于压力测试结论。

支持将旧 schema 2 的三测点记录迁移到九测点记录，原三个值对应区域 1，新增点标无效。未知格式会明确报错并保留数据。发生结果不确定的 NVS 写失败后停止继续复用记录槽，重启扫描恢复。MQTT 消息 ID 与连接代数匹配的 PUBACK 到达后才删除记录；Broker 确认不等于云端数据库确认。

## 7. UART V2 与快照同步

```text
A5 5A | version[1]=2 | type | seq_le16 | session_le16 | len | payload(0..32) | crc_le16
```

version 版本值为 2，占 1 字节。固定开销 11 字节，CRC 覆盖 version 到 payload。seq 是帧序号，request_id 是业务请求号，不能混用。

| 消息 | 类型 | 载荷字节数 |
| --- | --- | --- |
| STATUS | 0x01 | 29：启动标识、启停、周期、配置版本、存储状态、丢失计数、待补记数和最新事件号 |
| SAMPLE | 0x02 | 15：测点、质量、值、年龄、告警、配置版本 |
| RULE | 0x03 | 17：测点、下限、上限、回差、配置版本 |
| DEVICE | 0x04 | 6：地址、设备状态、配置版本 |
| COMMAND | 0x10 | 10：操作、参数、request_id、测点 |
| RESULT | 0x11 | 15：操作、结果、实际启停/周期、request_id、配置版本 |
| EVENT | 0x12 | 18：事件号、原 uptime/数值、测点/状态/类型/质量、原启动标识 |

收到新会话会清理旧投影；超过 3 s 无有效现场消息标为离线。命令回执同时匹配 session、seq、op、request_id。配置版本变化时清空同步进度，九测点、九规则及六设备属于当前版本且全部收到后才标记 `synchronized=true`。

F407 保存最近 8 个请求号，ESP32 保存 8 个请求状态槽；这是有限窗口的去重/查询，不是跨重启永久事务日志。未确认命令返回 UNCONFIRMED 并查询实际状态，不自动重放写命令。

## 8. HTTP 和 MQTT 使用

页面每 2 s 调用 `GET /api/status`。`POST /api/control` 带 `X-Gateway-Token`，受理后返回 HTTP 202 和 request_id；用同一令牌查询 `GET /api/commands/{request_id}`。状态为 PENDING/APPLIED/FAILED/UNCONFIRMED，旧完成槽可能被新请求回收。

```json
{"request_id":1001,"op":"period","period_ms":5000}
```

```json
{"request_id":1002,"op":"high","point_id":1,"value_scaled":350}
```

第二例将区域 1 温度上限设为 35℃；温湿度阈值使用十分之一单位，光照使用 lx。还支持 start、stop、low、hysteresis。阈值必须满足上下限、回差和量程约束。

MQTT 仍使用 `env/{device_id}/telemetry`、`status`、`config/set`、`config/state`；新增 `events` 和 `config/set/result`。遥测字段带 `zone1_`～`zone3_` 前缀，事件单独发布。命令 QoS 1、禁止 retain；每次只修改一个字段，request_id 为 1～536870911 的整数。

```json
{"request_id":2001,"sample_interval_s":5}
```

```json
{"request_id":2002,"point_id":7,"parameter":"high","threshold":350}
```

MQTT threshold 同样使用定点原始单位。上报周期用 `report_interval_s`，启停用 `collect_enabled`。逐条结果主题返回 request_id 与状态；实际配置主题包含版本和全部阈值。

## 9. IWDG、TIM7 和 CubeMX

**无需你先操作 CubeMX。** 当前看门狗由 `Services/Src/supervisor_service.c` 和 `Bsp/Src/board_system.c` 初始化：启动约 10 s 后启动 IWDG，/256、重装载值 2047，按 32 kHz LSI 估算约 16.384 s；实际受 LSI 偏差影响。每 250 ms 检查任务阶段期限，只有全部满足才刷新。调试暂停时冻结 IWDG，避免单步时反复复位。

StorageTask、事务等待与采集休眠各有合理期限；仪表超时、Wi-Fi/Broker 离线不会直接禁止喂狗，任务卡死才会。最终必须用实际挂起任务、保持外部仪表离线等实验分别验证“会复位”和“不会误复位”。

TIM7 保留给 RTU 时序，50us 观察 DMA 进度，DWT 检查 t1.5/t3.5；任务仍按 1ms 消费字节和做协议校验。硬件 IRQ 仅观察索引与时间，不做 Flash 或协议处理。时序分辨率与中断延迟需要逻辑分析仪/从机台架验证。

以后重生成 CubeMX 时：

1. 打开原 `stm32f407.ioc`，保持 HSE 25MHz、系统时钟168MHz、HAL时基TIM6及现有串口/CAN/SPI/DMA 引脚。
2. 不再另行启用 IWDG 或 TIM7，不新增同名 `TIM7_IRQHandler`；若改用 CubeMX 管理，先删除相应手写初始化，避免双重管理。
3. Code Generator 保留 USER CODE；StorageTask 的创建和入口位于 `freertos.c` 的 USER CODE 区，原四任务仍由 CubeMX 管理。
4. 生成后保留顶层 CMake 对 `cmake/nursery_layers.cmake` 的引用；核对该文件的 Application、Services、Protocol、Drivers/Device、BSP 和 shared 层源文件/头文件路径。
5. 重新构建并核对 `TIM7_IRQHandler` 仅一个定义，UART2/3 RX DMA 仍为循环模式，相关 FreeRTOS 中断优先级不低于数值 5 的限制。

**这次必须配套更新两板，ESP32 还要更新分区表。** UART V1/V2 不兼容；只执行应用 OTA 不会更新分区表。首次使用完整有线烧录，在设备管理器确认串口后执行 `idf.py -B build_nursery -p COM实际编号 flash monitor`。不要加 erase-flash：现有凭据和待发记录应保留并迁移。F407 用 CMSIS-DAP 和 STM32F4 的 OpenOCD 配置烧入本次 ELF，不能套用 ST-Link interface。

本次未自动烧录，也没有访问 Broker 或发送遥测。首轮跨协议升级若回退到旧 V1 ESP32 镜像，网关将无法解析 V2 现场帧，F407 本地采集仍独立运行；保留有线恢复入口。后续 OTA 应在前后镜像均使用 V2 的基线上验证。

验收顺序：两板启动与存储状态 → 无仪表故障降级 → 实际仪表寄存器与单位 → 六设备离线/恢复 → 阈值确认/回差 → 配置保存与重启 → 事件断线追补 → Broker/PUBACK 与满队列 → IWDG 任务挂起 → OTA 成功及回滚。构建和主机测试通过不替代这些实机结果。
